Architectural Blueprint: Robust Agent Loop for Local LLM Code AssistantsExecutive Summary & Architectural DiagnosisDeploying autonomous software engineering agents powered by open-weight local Large Language Models (LLMs)—such as Qwen 3.6 35B or Gemma 4 31B—requires a specialized context management paradigm. Traditional cloud API-based agents often rely on massive context windows and server-side optimizations. In contrast, single-phase agentic loops executing research, planning, code mutation, and terminal testing in a continuous conversation thread fail on local hardware due to catastrophic token accumulation and severe model context rot.Empirical telemetry from single-phase execution logs reveals that input prompt re-reading accounts for 88% to 96% of total token processing per run, with a read-to-write tool invocation ratio exceeding 30:1. Because every step re-transmits source files, search logs, and historical tool outputs back through the model, token processing scales quadratically $O(n^2)$ relative to step count $n$.When executing over small open-weight models, this history expansion causes three primary systemic failures:Time-To-First-Token (TTFT) Latency Spikes: Self-attention computation scales quadratically $O(n^2)$ with sequence length. Re-reading 200,000+ tokens per step exhausts local GPU throughput.Context Rot ("Lost-in-the-Middle"): Model attention degrades over long context sequences. Critical operational rules, architectural invariants, and safety constraints buried in historical search logs are frequently ignored.Reactive Guard Over-engineering: To control runaway execution loops, systems accumulate layers of reactive runtime guards (e.g., StepBudget, ReadBudget, compactMessages, EmptyResultStreak). These guards address symptoms rather than the root cause: mixing research (discovery) and code writing (implementation) within a single memory context.This blueprint presents a final, feedback-refined architecture: a decoupled, two-phase (Gather/Apply) agent loop combined with deterministic Markdown context chunking, a persistent Task Blackboard, hybrid RAG, lazy re-indexing, and epoch-validated state gates.Decoupled Two-Phase Execution Architecture (Gather & Apply)To eliminate quadratic context growth, the agent loop decouples discovery from execution. ### State Gates, Lazy Re-indexing & Multi-Node Continuity

1. **Monotonic Epoch Counter**: An integer tracking workspace mutations. Bumps whenever workspace source files or chunks are modified.
2. **Pre-Apply Epoch Gate**: Before the Apply phase modifies target paths, the orchestrator verifies that `epoch` values declared in the `NodeBrief` match the active Master Index. If a mismatch occurs, execution halts immediately to prevent writing against stale assumptions, triggering a low-cost re-gather sequence.
3. **Lazy Re-indexing**: Re-chunking files and updating vector embeddings after every write operation introduces index churn cascades. Under lazy re-indexing, write operations bump file/chunk epochs immediately, but full re-chunking and vector re-embedding are deferred until node execution completes or pre-commit verification gates run.
4. **Persistent Task Blackboard (`.aca/task_state.json`)**: To prevent multi-node context loss across complex sequential workflows (spanning 5 to 10 nodes), global project invariants, high-level objectives, and completed node summaries are recorded in a persistent blackboard file. This state is injected into all Gather and Apply prompts alongside the `NodeBrief`.

## Gather-Phase Hybrid Local RAG Subsystem

Retrieval-Augmented Generation (RAG) is integrated exclusively within the Gather phase to augment discovery without polluting the Apply context window.

### Technical Workflow for Hybrid RAG

1. **Hybrid Retrieval Engine**: Combines dense vector $k$-Nearest Neighbors ($k$-NN) search with sparse lexical matching (`grep` / BM25). Dense vectors retrieve conceptual matches, while sparse lexical queries capture exact code symbol names, interfaces, and function signatures.
2. **Snippet Extraction**: Slices retrieved files into bounded passages (200–400 tokens) accompanied by provenance metadata (file path, byte range, score, epoch).
3. **Context Fencing**: Snippets inside the `NodeBrief` are enclosed in boundary tags to instruct models to treat retrieved text as evidence rather than executable instructions:

```text
<<<UNTRUSTED_DATA>>>
Source: src/auth/jwt.ts (Bytes: 1024-1450 | Epoch: 14)
Snippet:
export function verifyToken(token: string): TokenPayload {
  return jwt.verify(token, process.env.JWT_SECRET!) as TokenPayload;
}
<<<END_UNTRUSTED_DATA>>>
